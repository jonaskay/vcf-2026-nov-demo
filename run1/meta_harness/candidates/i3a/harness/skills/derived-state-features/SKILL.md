# Derived-state features (activity/time based states)

- Define the state as a pure function of timestamps/events: a SQL scope and a Ruby predicate that give the same answer (test that they agree on every fixture case). A state that "begins after N days of quiet" appears by the clock passing, with no job and no stored flag, if the needed timestamps already exist.
- Look for existing machinery first (activity spikes, `last_active_at`, events, entropy periods, statuses). Reuse its thresholds and helpers rather than recomputing differently.
- Order matters in "X, then Y": anchor Y to the time of the LAST X. "A burst then N days quiet" means no activity since the burst for N days; activity after it clears the state until a new X occurs and a new quiet period elapses. Test: X, quiet N days -> on; X, activity at N-1 days, quiet N-1 more days -> off; then a new X, N quiet days -> on.
- "Any activity" = everything that touches `last_active_at` (comments, events, reactions, assignments, reopen, publish). Test at least two different kinds.
- Thresholds are literal: "three or more" is `>= 3`, "within X" is inclusive of the window edge; test just inside and just outside. "From at least two people" means distinct users (ignore system user comments). Windows relative to a configurable value (board/account period) read it from the record, not a constant.
- "Wherever cards are shown": `grep -rn "card" app/views -l`, list every card partial (previews, public previews, perma/container, columns, notifications, JSON/jbuilder) and add the indicator to each with the same markup/key; add the state to fragment cache keys. Prove it with a request test that asserts the rendered page and the JSON.
- New list filter value: add it to the filter's allowed list, map it in `indexed_by`, check any `include_*` helpers on the filter that hide closed/postponed cards, and make params round-trip (labels/JSON that enumerate values). Prove it with a controller test using `?indexed_by=<value>`.
