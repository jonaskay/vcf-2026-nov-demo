## Transferable lesson

- **cue**: Base runs of a multi-part feature request spend tens of minutes in long single reasoning turns, reading and designing before the first file write, so wall-clock time rather than correctness is the binding constraint.
- **lesson**: In system.md, replace the generic analyze/reproduce/fix workflow with a clock-anchored loop: `date -u` in the first command and at every test run, explicit minute and step deadlines (first test or migration by about minute 20, everything implemented by about minute 55, finish-only after about minute 75), and an exploration stop rule ("done once you know which files you will touch and which test covers each behaviour"). Then check that the first repository write lands within the first ~10 steps.
- **evidence**: system.md row (inv/adopted): all 3 inv runs wrote first at steps 9–11 (+3.5 to +6 min) and finished in 21–34 min. Base runs wrote first at +39 to +41 min after 9–10 minute think turns (base r2 step 10→11, base r3 step 9→10) and took 42–76 min. The skill row (dom) is confounded and is not used.
- **confidence**: medium. The contrast holds in 3 of 3 runs against 3 of 3, and the timing behaviour is directly tied to the rule's `date -u` and deadline text. But the same file also added workspace facts, so the two parts are not isolated, and only speed and process are observed here, not output quality.
